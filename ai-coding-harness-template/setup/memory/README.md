# 영속 메모리 (Auto Memory) 운영 규칙

> Claude Code 가 **세션과 세션 사이에 맥락을 기억**하는 개인 저장소의 운영 규칙.
> 리포에 커밋되는 문서 하네스와는 **다른 계층**이다. 경계를 먼저 잡고 시작한다.
> <!-- 이 문서는 규칙만 담는다. 실제 메모리 내용은 각자의 머신에 쌓인다. -->

## 문서 하네스와 무엇이 다른가

| 구분 | 문서 하네스 (`CLAUDE.md`, `docs/`) | 영속 메모리 (`memory/`) |
|------|-----------------------------------|------------------------|
| 위치 | 리포 안, git 추적 | 홈 디렉터리, git 밖 |
| 소유 | 팀 공동 | 개인 머신 1대 |
| 내용 | 규칙·구조·컨벤션 — "이렇게 해야 한다" | 맥락·경위·선호 — "지난번엔 이랬다" |
| 수명 | 프로젝트와 함께 산다 | 맥락이 끝나면 지운다 |
| 작성 | 사람이 합의해서 쓴다 | AI 가 대화 중 자동으로 쌓는다 |
| 검증 | 리뷰·PR | 없음 → **위생 관리가 필수** |

- **판단 한 줄**: 팀원 누구에게나 적용되면 문서, 나에게만 해당하면 메모리.
- 메모리에 팀 규칙을 적으면 "나만 아는 규칙"이 된다. 그건 승격 대상이다(아래 승격 기준).
- 문서 하네스 자체의 거버넌스는 [`docs/DOC_GARDENING.md`](../../templates/docs/DOC_GARDENING.md) 소관. 여기서 재서술하지 않는다.

## 저장 위치와 경로 슬러그

```
~/.claude/projects/<경로슬러그>/memory/
├── MEMORY.md                  # 인덱스 — 세션 시작 시 로드
├── user_<주제>.md
├── feedback_<주제>.md
├── project_<주제>.md
└── reference_<주제>.md
```

- **슬러그 규칙**: 프로젝트 절대경로의 영숫자 이외 문자를 전부 `-` 로 치환. **대소문자는 그대로.**
  `예: C:/src/acme-web → C--src-acme-web` (`:` 와 `/` 가 연달아 `--` 가 된다)
- **⚠️ 함정**: 같은 폴더라도 `c:/src/...` 로 진입하면 `c--src-...` 라는 **다른 슬러그**가 생겨 이전 메모리를 못 읽는다.
  프로젝트 진입 경로 표기를 하나로 고정한다.
- `MEMORY.md` 는 **첫 200줄 또는 25KB 까지만** 세션 시작 시 로드된다. 초과분은 안 읽힌다 → 인덱스는 짧게.
- 관련 설정 키: `autoMemoryEnabled`(기본 `true`), `autoMemoryDirectory`(저장 경로 변경).

## 파일 하나 = 사실 하나

- 노트 1개 = 주제 1개. 두 주제가 섞이면 한쪽만 낡아도 파일 전체를 못 믿는다.
- 파일명은 `<type>_<주제>.md`. 인덱스에서 유형이 바로 보인다.
- frontmatter 는 아래 한 형태로 고정한다.

```yaml
---
name: <파일명과 같은 식별자>          # 예: project_payment_refactor
description: <한 줄 요약 — 인덱스에 그대로 쓸 수 있는 문장>
metadata:
  node_type: memory
  type: <user | feedback | project | reference>
---
```

  <!-- `type:` 을 최상위에 두는 구형 형태도 동작하지만 섞어 쓰지 않는다. 위 형태 하나로 통일할 것.
       세션 ID·수정시각 같은 값은 AI 가 채운다. 손으로 쓰지 않는다. -->

## 네 가지 type

| type | 담는 것 | 필수 규칙 |
|------|--------|----------|
| `user` | 사람에 대한 정보·선호 | 프로젝트가 바뀌어도 유효한 것만. 프로젝트 사정은 `project` 로 |
| `feedback` | 작업 방식 교정 | **Why(왜 틀렸나) + How to apply(다음엔 어떻게) 둘 다** — 한쪽만이면 재발 |
| `project` | 진행 맥락·목표·제약·결정 | **상대 날짜 금지** → 절대 날짜(`YYYY-MM-DD`). 끝나면 삭제 또는 승격 |
| `reference` | 외부 자원 포인터 | 내용 복사 금지, **포인터만**. 원본이 정본 |

## MEMORY.md 인덱스

- 인덱스는 **포인터만**. 본문 금지 — 200줄 예산을 잡아먹고 노트와 이중 관리가 된다.
- 한 줄 형식: `- [<제목>](<파일명>.md) — <한 줄 훅>`
- 훅은 요약이 아니라 **"이 노트를 열어야 할 이유"** 다.
- 인덱스에는 frontmatter 를 쓰지 않는다. 실물 예시는 [`MEMORY.example.md`](MEMORY.example.md).

## 상호링크

- **노트 본문끼리는 `[[<name>]]`** — frontmatter 의 `name` 값이지 파일명·확장자가 아니다.
- **인덱스에서는 일반 마크다운 링크.** 두 규칙을 섞지 않는다.

## 무엇을 저장하지 말 것

- **리포가 이미 기록하는 것** — 디렉터리 구조, 클래스 목록, 커밋 이력, 브랜치 목록. 명령 한 번이면 나온다.
- **`CLAUDE.md`·`docs/` 규칙의 복사본** — 규칙이 바뀌면 메모리 쪽만 낡는다. 링크도 필요 없다(AI 가 이미 읽는다).
- **이번 대화에서만 쓰는 값** — 임시 경로, 스크래치패드, 일회성 명령.
- **자격증명·접속정보** — 호스트·계정·비밀번호·토큰. 메모리는 평문 파일이다
  (→ [`docs/SECURITY.md`](../../templates/docs/SECURITY.md)).
- **미확인 추측** — 안 적거나, 적을 거면 "미검증"이라고 같이 적는다.

## 메모리 위생

> stale 메모리는 없는 것보다 나쁘다. AI 가 **틀린 사실을 근거로 확신 있게** 움직인다.
> 이 계층 최대의 리스크는 용량이 아니라 노후화다.

정기 점검(월 1회 또는 대규모 리팩터링 직후):

- [ ] 노트가 가리키는 **파일 경로·URL 이 아직 존재하는가**
- [ ] 인덱스의 링크 대상 노트가 실제로 있는가 — 반대로 인덱스에 없는 고아 노트는 없는가
- [ ] 끝난 작업의 `project` 노트가 남아 있지 않은가
- [ ] 같은 사실이 두 노트로 갈라져 있지 않은가 → 병합
- [ ] 상대 날짜("지난주", "어제")가 남아 있지 않은가 → 절대 날짜로

실제 사례: 리팩터링으로 사라진 문서를 가리키는 노트가 인덱스에 그대로 남아, 이후 매 세션 AI 가
없는 경로를 먼저 열고 실패한 뒤 엉뚱한 파일을 대신 추정했다. **틀린 노트는 고치지 말고 지운다** —
고칠 근거가 없으면 삭제가 정답이다.

## 새 환경으로 옮기기

- 메모리는 **머신 로컬**이다. 리포를 clone 해도 따라오지 않는다.
- 옮길 때는 `~/.claude/projects/<슬러그>/memory/` 폴더만 복사한다. 그 상위의 상태 파일·세션 로그는 복사 금지.
- **새 머신의 프로젝트 경로가 다르면 슬러그도 다르다.** 폴더명을 새 경로 기준 슬러그로 바꿔야 인식된다.
- 이사 전에 위생 점검부터. 죽은 메모리를 옮기지 않는다.

## 리포 문서로 승격하기

| 기준 | 메모리에 남긴다 | `docs/` 로 승격 |
|------|----------------|----------------|
| 적용 범위 | 나 / 내 머신 | 팀원 누구에게나 |
| 수명 | 이 작업·이 스프린트 | 프로젝트가 사는 동안 |
| 근거 | 경험칙, 1회 관찰 | 코드·설정으로 확인된 사실 |
| 재발 | 처음 겪음 | **같은 교정이 3회 이상** |
| 형태 | 포인터·경위 메모 | 절차·규칙·금지 |

- 승격은 복사가 아니다. `docs/` 에 쓰고 **메모리 노트는 지운다**. 인덱스 줄도 지우거나 리포 문서 링크로 바꾼다.
- 어느 문서로 보낼지, 승격 후 무엇을 같이 갱신할지는 [`docs/DOC_GARDENING.md`](../../templates/docs/DOC_GARDENING.md) 의
  위치 규칙과 갱신 트리거를 따른다.
